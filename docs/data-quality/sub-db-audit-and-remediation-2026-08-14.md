## النتيجة التنفيذية

الخدمة يجب أن تصنف النص إلى **صنف نهائي قابل للاختيار من `good_types`**، لا إلى منتج ولا إلى جذر عام. إذا لم يوجد دليل كافٍ، ترجع `directGoodType=null` مع مراجعة وبدائل. لا يوجد fallback إلى ID 31.

المشاكل الحالية ليست مشكلة موديل واحدة. يوجد خلل في البيانات، والهيكل، والاسترجاع، وقياس الثقة، وجدول التصحيحات. تغيير موديل الـEmbedding وحده لن يحلها.

## مشاكل هندسة `new_good_types`

### مشكلة الربط

الجدول يحتوي:

```text
id, name, assigned, created_at, updated_at, user_id
```

ولا يحتوي `selected_good_type_id`. لذلك لا يمكن إثبات أن النص المعيّن اختير له ID 14 أو 56 أو 171. هذا يجعل البيانات غير صالحة لتدريب supervised classifier موثوق.

الحد الأدنى المقترح في التطبيق الأساسي:

```text
classification_feedback
  request_id                 UUID/unique
  raw_text                   text
  normalized_text            text
  predicted_good_type_id     FK nullable
  selected_good_type_id      FK nullable
  review_status              PENDING|VERIFIED|REJECTED
  reviewer_id                nullable
  catalog_version            string
  model_version              string
  policy_version             string
  evidence_json              json
  created_at / reviewed_at
```

لا يتعلم production مباشرة من النقر. تدخل فقط السجلات `VERIFIED` في dataset offline.

### مشكلة التكرار والبحث

- لا يوجد index على `name` أو `assigned`.
- لا يوجد normalized fingerprint أو idempotency key.
- أسماء متطابقة تُسجل عشرات المرات؛ أمثلة: `مواد البناء والتشييد اسمنت` 84 مرة، `بطاطا اكياس` 83، `فوسفات` 60، و`طحين` 53.
- أرقام مفردة مثل `25`, `24`, `10` متكررة ولا تحمل صنفاً.
- توجد أسماء مكان/حالة عامة مثل `الرياض` و`جيد` لا تمثل بضاعة.
- يوجد 494 اسماً normalized له صفوف assigned وغير assigned معاً، فلا يمكن اعتبار الـBoolean حقيقة تعلم مستقرة.

الحل: فصل **event log** غير القابل للحذف عن **review item** الموحّد، وفهرسة normalized fingerprint، وربط قرار المراجع بالصنف النهائي.

## سياسة Fuzzy الصحيحة

### ممنوع

- استخدام `partial_ratio` عندما أحد الطرفين أقصر من 4 أحرف.
- اعتبار تطابق حرفين دليلاً قوياً.
- السماح لـ`بط` بالفوز على `بطاطس` بسبب substring.
- عرض score الفزي كنسبة دقة.
- auto-accept من Fuzzy وحده في الـMVP.

### مسموح

1. exact على النص normalized والـaliases.
2. variants غير مدمرة: تكرار الحروف، مسافات البراند، وصرف عربي محافظ.
3. Fuzzy كامل token-aware باستخدام normalized edit similarity، مع:
   - exact فقط إن كان الطرف الأقصر أقل من 4؛
   - حد أدنى لتناسب الطول؛
   - حد أقصى للمسافة التحريرية حسب طول الكلمة؛
   - عقوبة للكلمات غير المغطاة؛
   - منع two-character anchors.
4. Fuzzy يبني Top-K ولا يتخذ القرار.
5. القبول يتطلب exact/variant قوي أو اتفاق lexical + semantic/rerank مع margin ومعايرة.

## سياسة Embedding/Reranking الصحيحة

- بناء document مستقل لكل direct leaf type، لا document واحد للجذر.
- document يحتوي الاسم العربي المباشر، اسم الجذر، aliases منقحة، ووصف حدود الفئة.
- استبعاد English labels غير المراجعة.
- مقارنة E5-small الحالي مع BGE-M3 وJina v3 على gold set دندن نفسه.
- استخدام reranker online فقط للحالات غير المحسومة؛ exact لا يدفع تكلفة online.
- timeout أو فشل provider = بدائل محلية + review، وليس قبولاً.
- raw cosine هو ترتيب تقارب، وليس probability.
- calibrator offline ينتج `decisionConfidence` بعد اختبار temporal holdout.

```text
1. Quarantine أخطاء البيانات + leaf-only catalog
2. direct-type fusion + nullable API + no ID 31

4. guarded token-aware fuzzy
5. source-level semantic documents

7. calibrated accept/review
```
