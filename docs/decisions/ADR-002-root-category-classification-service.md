# ADR-002: خدمة تصنيف الصنف الرئيسي للبضاعة

## الحالة

مقترح للتنفيذ

## التاريخ

2026-08-13

## القرار

نبني خدمة خارجية مستقلة تستقبل نص البضاعة الذي يكتبه السائق، وترجع **الصنف الرئيسي فقط** من جدول `good_types`، أي الصفوف التي يكون فيها `parent_id = NULL`.

حسب ملف قاعدة البيانات الحالي يوجد في `good_types` عدد `103` نوعاً، منها `37` صنفاً رئيسياً. أي اسم فرعي أو اسم شائع أو براند معروف يستخدم فقط كدليل بحث، ثم ترفع النتيجة إلى الصنف الرئيسي.

مثال: `نيدو` أو `حليب بودرة` أو `كيت كات` لا نحتاج أن نطابقها كمنتج نهائي؛ المطلوب إرجاع الجذر المناسب مثل `12 - مواد غذائية` إذا كان الدليل كافياً.

## لماذا تغير القرار؟

القرار السابق كان يعالج مطابقة نوع/منتج وإرجاع فئة نهائية `leaf` مع تدفق تأكيد ومراجعة داخل تطبيق السائق. بعد توضيح النطاق، المنتج نفسه غير مهم، والتطبيق الأساسي سيتكفل بكل شيء بعد أن يستلم الصنف الرئيسي.

لذلك نقلل التعقيد:

- لا نطابق المنتج ذاته.
- لا ننشئ أنواعاً جديدة.
- لا نبني Review Queue داخل هذه الخدمة.
- لا نستخدم Agent أو LangGraph في الـMVP.
- لا نعتمد على بحث الإنترنت في مسار الطلب.
- لا نحتاج Vector Database لحجم الكتالوج الحالي.

## المعمارية المختارة

نستخدم مسار Hybrid Retrieval محلي وسريع:

1. تطبيع محافظ للنص مع حفظ النص الأصلي.
2. كشف اللغة: عربي، إنجليزي، مختلط، أو لغة أخرى.
3. تطابق حرفي مع أسماء الجذور وأسماء الأبناء و`common_names`.
4. بحث إملائي باستخدام fuzzy/character n-grams.
5. بحث دلالي باستخدام embedding محلي متعدد اللغات.
6. دمج النتائج وتجميعها على `root_good_type_id`.
7. سياسة قرار ترجع أفضل صنف رئيسي مع `requiresReview`.

## عقود السلامة

- `good_types` هو مصدر الحقيقة الوحيد للـIDs.
- لا تعاد إلا IDs موجودة كجذور رئيسية.
- لا توجد قيمة fallback مثل ID 31.
- إذا كان النص بلغة غير مدعومة أو الدليل ضعيفاً، تعود الخدمة بنتيجة مرشحة مع `requiresReview = true`.
- التشابه الدلالي ليس نسبة ثقة؛ يستخدم للترتيب فقط.
- API key مطلوب عند استخدام الخدمة من تطبيق دندن.

## العواقب

الإيجابيات:

- أبسط وأسرع من Agent أو LLM في كل طلب.
- مناسب للـMVP لأن الكتالوج صغير ويمكن تحميل الفهرس في الذاكرة.
- يدعم الأخطاء واللهجات وتعريب البراندات بقدر جيد عبر fuzzy + embeddings.
- يمكن ربطه لاحقاً بزر "إضافة جديد" في التطبيق من دون تغيير منطق التطبيق الأساسي.

التنازلات:

- البراند غير الموجود فعلياً سيعود غالباً كـ`LOW_EVIDENCE` أو `AMBIGUOUS`.
- الوصول إلى قرار آلي بلا مراجعة يحتاج gold set من بيانات دندن.
- اللغات خارج العربي/الإنجليزي تقبل كمدخل، لكن لا تعتبر مدعومة رسمياً في الـMVP.
